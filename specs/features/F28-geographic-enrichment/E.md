# F28-E — Exploratory proximity

Core implements a separate exploratory API over enrichment representations; UI adds clearly labeled opt-in exploration only after that contract. Point/facility estimates and endpoint-derived separation remain approximate; area extents support overlap/possible neighborhood, not precise center-distance ranks. Unknown owners are visible and never presumed distinct. Preserve strict engine/output and exclude benefit/route/construction assertions. Reuse authoritative geographic primitives and document uncertainty semantics before implementation.

Dependencies, owner, exact file boundaries and observable acceptance are fixed in [the parent spec](spec.md). Coordinator owns shared changes and sole bounded checks.

## Selection-driven first increment (committed before worker dispatch)

`app/src/domain/exploratory.ts` defines the shared transient result/UI props. Core owns only new `app/src/core/exploratory.ts` and `changes/F28-exploratory-core.md`. UI owns only new `app/src/features/explorer/ExploratoryResults.tsx` and `changes/F28-exploratory-ui.md`. Root owns App/Explorer/ComparisonPanel integration and the shared contract. No strict engine, schema, persistence, map or package edits.

Core exports `analyzeExploratoryProximity(projects: readonly Project[], records: readonly GeographicRecord[], selectedProjectId: string, radiusMiles: number): ExploratoryAnalysis`. One selected project is compared with the entire current collection in linear time; do not build a quadratic all-pairs area list. Only current validated companion rows with represented status participate; foreign IDs and unresolved rows do not fabricate geometry. Invalid radius throws; a missing/unresolved selection yields an empty result with a specific reason. No source mutation or implicit Project.location fallback.

Point pairs use the canonical haversine implementation and retain full precision for the strict radius comparison. If either representation is endpoints, `endpoint-distance` is the smallest separation between supplied point/endpoints, explicitly a sampled endpoint separation rather than route/project-center distance. Reuse authoritative timing. Area/area intersecting extents yield `extent-overlap`; area/point or area/endpoints containment yields `within-extent`. These two relations have null distance and are bounding-extent context only; the radius does not qualify them. Outside extents produce no distance assertion. No centroid, invented accuracy or benefit ranking. Return every matching row with stable ordering (numeric separations first by distance/ID, coarse context after by ID); UI paginates rather than silently truncating.

Ownership stays unknown unless both cited owner identities can be compared within compatible identity scopes. Same IDs only establish same owner within the same inventory or global scopes; differing IDs establish distinct owners only within one source inventory or when both are globally scoped. Missing owner, filing/sponsor labels or source-scoped identities across inventories stay unknown. Preserve record kind/lifecycle/representation limitations in result context; exploration is allowed for context records with a clear limitation and is never a strict candidate.

UI consumes `ExploratoryResultsProps`, uses default components, concise explicit exploratory labels, source project identification, distance units/meaning or coarse overlap text, ownership/timing context and limitations. Every result remains reachable through internal pagination/scroll; preserve component draft/page context across ordinary parent renders. Root places this as a meaningful opt-in topic for a single selected project in the existing panel and passes the applied scenario radius; strict Candidates, saving and impact behavior stay intact. UI does not calculate distances, overlap, ownership or timing. No worker checks.
