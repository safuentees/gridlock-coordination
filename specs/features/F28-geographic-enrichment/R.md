# F28-R — Review and repeatable updates

Deliver separate cached companion storage and export first. The cache/export and repeat-processing controller are connected. Next, export `GeographicReviewInput = { inputFingerprint, decision, reason, representation? }` and `reviewGeographicOutcome(run, projectId, input)` from `app/src/enrichment/review.ts`; return a schema-validated new run and never mutate the input. Compare the caller fingerprint to the active record so a stale UI action cannot update a replacement row; an explicit re-review can target the current fingerprint. Accept preserves the current representation; reject preserves it in review metadata while removing it from active output; correct requires a complete cited representation. Do not silently replace a more precise prior representation with a weaker correction. A review binds to the source fingerprint, not generated time.

After the core API is frozen, root exposes `onReview(projectId, input): Promise<void>` through `use-geography.ts` and writes it through the separate `geography-session.ts` store. It resolves only after persistence succeeds and rejects guard/storage failures after exposing a concise error. UI adds accept/reject/correct controls in the selected record detail in `GeographyPanel.tsx`, with an accessible confirmation/reason and source details for corrections. Keep per-mode search/filter/page/selection, list scroll, unsaved correction draft and the existing Readiness editor state. Companion import must preview mode, collection identity, changed inputs and review conflicts before replacing saved geography; malformed or conflicting data must preserve the existing saved copy. Retain failures/ambiguity for repeatable updates. Exact boundaries remain the parent contract's R paths.

Dependencies, owner, exact file boundaries and observable acceptance are fixed in [the parent spec](spec.md). Coordinator owns shared changes and sole bounded checks.
